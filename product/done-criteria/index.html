    Done Criteria¶

    What "the product is done" means at the product level, as distinct from "this task is done".

    The Project Manager tracks completion at five levels and must not conflate them:

    task done      -> this issue's acceptance criteria are met
feature done   -> the capability works end to end for a user
milestone done -> every capability in the milestone is done
MVP done       -> every MVP capability below is done
product done   -> every criterion in this document is satisfied

    A finished task is not a finished product. The most common failure mode of an autonomous delivery loop is concluding "done" because the queue emptied, or because a large issue merged. Neither means the roadmap advanced.

    Product-level completion criteria¶

    The product is done when all of the following hold. Each is binary and independently checkable.

    1. The MVP chain works end to end¶

    Every link in the chain from docs/product/mvp.md works, in order, for a real household with real data:

    Authentication -> Household -> Invite members -> Create expense
-> Choose participants -> Split expense -> Calculate balances -> Settle debts

    Not "the endpoint exists" — the flow completes, and the data is correct afterwards.

    2. The financial core is exact¶

    • Money uses exact decimal arithmetic. No double, no float.
    • Currency is explicit everywhere, never inferred silently.
    • Rounding rules are defined, documented, and covered by tests that assert specific values.
    • Splits sum exactly to the expense total. No lost or invented minor units. Remainder distribution is deterministic.
    • Balances derive from expenses and are consistent with them.
    • Settlements reflect settled amounts correctly and do not double-count.

    This is non-negotiable and is treated as HIGH risk throughout. A rounding error that is "close enough" fails this criterion.

    3. Household isolation holds¶

    • A member cannot read or write another household's data by changing an identifier in a request.
    • Isolation is enforced server-side, not only in the UI.
    • The rule is covered by tests that attempt the cross-household access and assert refusal.

    4. Authentication and authorization are real¶

    • Authentication is implemented and enforced.
    • Authentication and authorization are separate concerns, both present.
    • Secrets are never committed, logged, or exposed to clients.

    5. Quality gates are green¶

    • ci is green on main.
    • Every feature has tests: unit for domain logic, integration for persistence, API tests for important endpoints.
    • No skipped, deleted, or tolerated test exists in the financial paths.
    • Code review and security review have passed for the security- and money-sensitive changes.

    6. The product is usable¶

    • The published prototype's core flows correspond to implemented behaviour, and prototype feedback has been resolved or explicitly deferred with a reason.
    • UX validation has passed for user-facing work.
    • Required documentation is current: docs/product/, docs/architecture/.

    7. The delivery system is itself trustworthy¶

    • The agent workflow, autonomy policy and budget are documented and enforced.
    • No work item is stranded: every open issue has an owner and a next action.
    • No duplicate work exists between open and recently closed issues.

    8. Nothing is quietly deferred¶

    Anything not done is written down, with a reason. Silent scope reduction is a failure of this criterion — an honest deferral is acceptable, a hidden one is not.

    How the Project Manager uses this¶

    The manager must not mark the project done while any criterion above is unmet, and must not treat "the backlog is empty" as evidence. When it believes the product is approaching done, it should:

    1. check each criterion explicitly against evidence, not assertion
    2. report which criteria are met, and which are not
    3. for unmet criteria, create or update the work that closes them
    4. leave the final call to the founder — declaring the product done is a product decision, not a delivery one

    Explicitly not criteria¶

    These do not count toward done, however complete they are:

    • number of merged PRs
    • number of closed issues
    • a green build with no tests
    • documentation volume
    • a working demo that does not persist correct data
    • the absence of open issues
