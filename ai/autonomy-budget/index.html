    Autonomy Budget¶

    Hard limits that keep autonomous execution bounded. The manager must stop gracefully when a limit is reached — never exceed a budget to "finish" something.

    Limits are repository variables, so they can be tuned without a code change. A missing or empty variable means "use the default below", never "unlimited".

    Limits¶

    Variable Default Meaning
    MANAGER_MAX_NEW_ISSUES_PER_CYCLE 3 New feature issues created in one heartbeat.
    MANAGER_MAX_PRS_IN_FLIGHT 3 Open implementation PRs before the manager stops creating new work.
    MANAGER_MAX_CONCURRENT_AGENTS 2 Specialists the manager may have in flight at once.
    MANAGER_MAX_RETRIES_SAME_STRATEGY 2 Attempts with the same approach before reassessing.
    MANAGER_MAX_AUTONOMOUS_ATTEMPTS 3 Total attempts on one issue before it becomes status:blocked.
    MANAGER_MAX_CYCLES_PER_HOUR 4 Reconciliation cycles started in an hour.
    MANAGER_HEARTBEAT_MINUTES 30 Heartbeat interval, clamped to a floor of 15. Not applied to an explicit workflow_dispatch.

    Per the request that this system came from, "24/7" means continuously monitor and reconcile, not continuously create tasks. The issue cap is the main guardrail against that misreading.

    How the heartbeat interval is enforced¶

    GitHub Actions cron cannot read repository variables, so the schedule is fixed at 15 minutes in .github/workflows/project-manager-loop.yml and MANAGER_HEARTBEAT_MINUTES is applied at run time: the gate measures how long since the Manager Ledger was last updated and skips the cycle if it is inside the interval, clamped to a 15-minute floor.

    So the schedule is the cadence and the variable is the rate limit. Raising MANAGER_HEARTBEAT_MINUTES above 15 works immediately; lowering it below 15 does not, because the floor is deliberate. Changing the cadence itself means editing the workflow, which is a guardrail path and therefore always a human merge.

    An explicit dispatch is never throttled¶

    The interval applies to every trigger except workflow_dispatch. The rate limit exists to damp triggers that fire on their own — a CI completion, a label change, the clock — each of which can happen several times between two heartbeats. A dispatch is the opposite: a person pressed "run", by hand, on purpose.

    Throttling a request makes the loop untestable. Every fix needs a live cycle to prove itself, and if the human is the thing being throttled there is no way to get one without first waiting out the interval. So to test a change, dispatch the workflow and it runs now:

    /oc manager run

    or Actions → project-manager → Run workflow on main.

    The bypass is announced as a ::notice in the run and recorded in the Manager Ledger next to the result, so a cycle that overrode the throttle is always distinguishable from one that waited its turn.

    It skips the throttle and nothing else. The manager:paused emergency stop and MANAGER_AUTONOMY=human_only are evaluated before the interval and still apply to a dispatch. A cycle started by hand is still a gated cycle.

    MANAGER_MAX_CYCLES_PER_HOUR is not a shell limit — it is the manager's own bookkeeping — so repeated manual dispatches are not hard-capped. The oc-project-manager concurrency group still serialises them: a second cycle queues behind the first rather than running beside it.

    Which limits are enforced where¶

    Limit Enforced by
    MANAGER_HEARTBEAT_MINUTES shell gate (deterministic), except an explicit workflow_dispatch
    MANAGER_MAX_NEW_ISSUES_PER_CYCLE manager, against the ledger
    MANAGER_MAX_PRS_IN_FLIGHT manager, before creating work
    MANAGER_MAX_CONCURRENT_AGENTS manager, when delegating
    MANAGER_MAX_RETRIES_SAME_STRATEGY manager, from the ledger
    MANAGER_MAX_AUTONOMOUS_ATTEMPTS manager, from the ledger

    Only the stop conditions and the heartbeat interval are enforced in shell, because only those must hold even if the model misbehaves. The counting limits are the manager's own bookkeeping, exported into its environment as variables so it reads one source of truth instead of remembering numbers.

    What happens when a budget is reached¶

    1. Stop starting new work immediately.
    2. Record the remaining work in the ledger as queued for the next cycle, with the reason it was deferred.
    3. Report it in the cycle's output under ## Budget used.
    4. Do not retry the same action later in the same cycle.

    Exceeding a budget to finish something is a defect, not initiative.

    Failure and retry budget¶

    • Same strategy, maximum 2 attempts. After that, change something real: a different model, a different agent, a smaller task, or a split task.
    • Maximum 3 autonomous attempts per issue. On exhaustion, mark the issue status:blocked with evidence — what was tried, what failed, what is needed — and stop.
    • Never retry a status:blocked issue without an explicit human /oc continue.
    • Retries are counted in the ledger so the count survives a restart.

    Why these limits exist¶

    The failure mode being designed against is a runaway autonomous loop: an agent creates work, its own output triggers it, and the system generates work faster than it can converge. Recursion guards and idempotency checks reduce that risk, but a numeric ceiling is the only thing that actually bounds it. If the caps are routinely hit, the right response is to retune them or fix the sequencing — not to raise them reflexively.
