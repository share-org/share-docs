    Project State Model¶

    How the Project Manager derives project state.

    This is not a status file. Nothing here is edited by hand to record progress, and there is no machine-written state file in the repository. State is derived, on every run, from GitHub and the repository artifacts. This document describes the derivation so any human or agent can reproduce it.

    The reason this matters: the manager is a transient process. It must be able to start from zero and reconstruct the project. If state lived only in a model's context, a restart would silently lose it — and a manager that cannot remember what it already did will duplicate work.

    Sources of truth, in precedence order¶

    1. Human instruction — a direct comment from the founder. Always wins.
    2. GitHub labels on issues — authoritative for the state of actual work.
    3. Merged PRs and green CI — authoritative for what is genuinely complete.
    4. docs/product/done-criteria.md — authoritative for "product done".
    5. docs/product/roadmap.md — authoritative for intended order and scope. Its execution-status column is a mirror maintained by the manager.
    6. docs/architecture/decisions/ — authoritative for settled decisions.
    7. docs/product/mvp.md, vision.md, docs/ux/, docs/ai/ — context.

    When two sources disagree, the higher one wins and the lower one is corrected. Labels beating the roadmap is the common case: the roadmap is documentation, the labels are reality.

    Work state machine¶

    BACKLOG
   ↓
DISCOVERY      (analysis, and brainstorming when a design decision matters)
   ↓
DESIGN         (product-planner + architect; UX via designer when relevant)
   ↓
READY          (specified and actionable — safe for an implementer to start)
   ↓
IN_PROGRESS    (an implementation agent is working, or a PR is open)
   ↓
QA             (qa-engineer verifying acceptance criteria)
   ↓
REVIEW         (code review, plus security review when required)
   ↓
READY_TO_MERGE (all gates green; merge-eligible, or awaiting the founder)
   ↓
DONE

    BLOCKED is a side state, not a step:

    any state → BLOCKED → (resume) the state it came from

    BLOCKED always carries evidence: what was tried, what failed, and what is needed. It is a legitimate outcome, not a failure to be avoided.

    Label mapping¶

    State Label
    BACKLOG status:backlog
    DISCOVERY status:discovery
    DESIGN status:discovery (the design and analysis labels are intentionally the same)
    READY status:ready
    IN_PROGRESS status:in-progress
    QA status:qa
    REVIEW status:review
    READY_TO_MERGE status:qa + status:review
    DONE status:done
    BLOCKED status:blocked

    Labels are created by scripts/setup-labels.sh.

    Manager state¶

    The manager's own bookkeeping — run log, budget counters, retry attempts, queued work — lives in a single Manager Ledger issue. An issue was chosen over a repository file because it is atomic, auditable, visible to the founder, and already covered by the label and concurrency machinery.

    "Pinned" here means identified by the manager:ledger label and never duplicated, not a GitHub UI pin: GitHub exposes no REST API for pinning issues, so the label is the only stable handle automation can resolve. The workflow finds the ledger by that label and creates it if it is missing, which makes "exactly one ledger" an invariant worth asserting rather than assuming.

    The ledger is the answer to "what did the manager already do, so it does not do it twice". Before any create/dispatch/merge, the manager checks it.

    Deriving the current state¶

    On each cycle the manager reads, in this order and no further:

    1. docs/ai/project-state.md (this file) and docs/ai/autonomy-policy.md
    2. the ledger issue
    3. issues filtered by state label — open ones, and status:blocked ones
    4. open PRs and their CI status
    5. recent merges (last ~20)
    6. prototype feedback issues
    7. docs/product/roadmap.md
    8. only then the specific files for the work in hand

    Filter by label before sending anything to a model. Reading every issue is both slow and a context-economics violation; the whole point of labels is that they let the manager select rather than ingest.

    Deriving progress against the roadmap¶

    For each roadmap capability, classify using evidence rather than assertion:

    Classification Evidence required
    completed a merged PR and green CI and the acceptance criteria demonstrably met
    in-progress an open issue in READY..REVIEW, or an open PR
    blocked status:blocked with recorded evidence
    missing no issue covers it
    obsolete superseded by a decision, or explicitly out of MVP scope
    next the earliest missing or obsolete-but-still-wanted capability whose dependencies are all completed

    next is the answer to "what should happen next", and it is the only input to the proactive-work decision. Dependencies come from the roadmap ordering and from Part of / feedback:child-of- relationships on issues.

    Deriving quality state¶

    CI failing on any open PR   → the owning issue is not progressing
QA failed or never ran      → the PR is not merge-eligible
review finding open         → delegate the correction, do not merge
security review absent on a HIGH/CRITICAL change → not merge-eligible

    Deriving "is it actually complete"¶

    A task is DONE only with all of:

    requirements satisfied
AND implementation complete
AND tests pass
AND QA passed
AND review passed
AND CI green
AND required UX / visual validation passed
AND required documentation updated

    An agent reporting "done" is a claim, not evidence. The manager verifies against merged PRs, CI and QA results.

    Completion is also a ladder, and the levels must not be conflated:

    task done      → this issue's acceptance criteria are met
feature done   → the user-visible capability works end to end
milestone done → every capability in the milestone is done
MVP done       → every MVP capability in docs/product/mvp.md is done
product done   → docs/product/done-criteria.md is satisfied

    Only the last one means the project is finished.

    Anti-patterns this model exists to prevent¶

    • Treating a merged PR as a completed feature.
    • Treating "no open issues" as "nothing left to do" when the roadmap has more.
    • Creating a duplicate task because the previous one was described in different words — hence: search open and closed issues before creating.
    • Keeping a private backlog in model context that no human can audit.
