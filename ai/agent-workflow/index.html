    Agent Workflow — reading the repository from GitHub¶

    This document explains how the SharedHousehold agent team operates and how a human owner runs the project from GitHub Issues and Pull Requests, with OpenCode executing behind the scenes in GitHub Actions.

    The pipeline at a glance¶

    Human (GitHub)
   │  creates / edits / comments an Issue
   ▼
GitHub Event / orchestration workflow
   │  (opencode-command.yml, opencode-issue-triage.yml, opencode-pr-review.yml,
   │   opencode-agent-status.yml)
   ▼
OpenCode Orchestrator (primary agent, runs in a GitHub Actions runner)
   │  task tool → product-planner / brainstormer / architect / implementers /
   │              qa / reviewers / security / documentation / researcher
   ▼
Implementation → branch → commits → Pull Request
   ▼
QA → Code review (→ security review when relevant)
   ▼
Human approval (default gate) → merge → CI (ci.yml) → done

    A second entry point feeds the same engine: the prototype feedback loop (maquette annotation layer → prototype-feedback issue → brainstorm panel → sub-issues → parallel chains). See "Prototype feedback loop" below.

    In autopilot mode (AUTOPILOT == 'on'), issues opened by trusted actors skip the per-phase /oc commands: opencode-pipeline.yml drives analyze → implement → qa → review and self-dispatches the next phase. The human merge gate, status:blocked halting, and /oc stop|continue overrides all still apply. See docs/ai/github-agent-commands.md.

    GitHub is the system of record. The repository is the system of knowledge (docs/, decisions, code). OpenCode is the execution engine and is deliberately transient — a new OpenCode process reconstructs state by reading GitHub and the repository.

    How an Issue moves through the system¶

    1. Issue created → triage¶

    opencode-issue-triage.yml runs on issues: opened. The orchestrator:

    1. reads the issue and relevant docs,
    2. decides whether a design decision is required,
    3. brainstorms if needed (writes docs/ai/brainstorms/BR-NNN-*.md, posts a concise summary on the Issue),
    4. marks the Issue status:ready (or status:discovery + open questions).

    Implementation is never started automatically. It requires an explicit /oc implement from a trusted human.

    2. Command¶

    A human comments /oc <command> (optionally /oc @agent <command>). The opencode-command.yml workflow validates the actor, assigns a run ID, posts a start/complete status on the Issue, and runs OpenCode.

    3. Implementation¶

    /oc implement → the orchestrator selects the implementation agent, creates a branch (feature/EXP-105-* or agent/<topic>-<agent>), commits with Git trailers (Agent, Agent-Run, Issue), opens a PR, and posts the PR link. When needed, /oc plan runs first: it writes docs/ai/plans/PLAN-*.md on a plan/<issue>-* branch and opens a PR that /oc implement then executes. Human approval remains the default merge gate.

    4. QA and review¶

    • opencode-pr-review.yml runs a read-only review automatically for human-authored PRs (skips bot-authored PRs to prevent self-review).
    • opencode-pr-review.yml and /oc qa / /oc review run the QA and review agents, which post PASS/FAIL evidence on the PR/Issue.

    5. Human approval¶

    The human reviews the PR in GitHub, asks for fixes via comments or /oc, and merges. CI (ci.yml, mvn verify) runs on every push/PR.

    Labels¶

    Status (the issue state machine)¶

    BACKLOG → DISCOVERY → READY → IN_PROGRESS → REVIEW → QA → DONE
                                ↘ BLOCKED
    Label Meaning Applied when
    status:backlog created, not started created
    status:discovery analyzing/brainstorming/planning triage, /oc analyze, /oc brainstorm, /oc plan, /oc decide
    status:ready specified, implementation can start triage completes with a sufficient spec
    status:in-progress implementation running /oc implement
    status:review pending code review /oc review, automatic PR review
    status:qa waiting for QA verification /oc qa
    status:blocked waiting on a human or external dependency /oc stop, a BLOCKED report
    status:done complete and merged merged

    Type¶

    type:feature, type:bug, type:architecture, type:technical-debt, type:brainstorm.

    Priority¶

    priority:p0 (blocker) … priority:p3 (lowest).

    Agent (logical identity)¶

    agent:orchestrator, agent:product, agent:architect, agent:backend, agent:frontend, agent:qa, agent:security, agent:review, agent:documentation. These record which logical agent is/was active — there is one automation identity, not fake per-agent users.

    Prototype feedback¶

    Label Meaning Applied when
    prototype-feedback filed from the published maquette's annotation layer by the human, through the prefilled issue URL
    feedback:parent a feedback issue already fanned out into sub-issues by the intake run
    feedback:child sub-issue derived from a parent feedback issue by the intake run
    feedback:child-of-<issue> the parent link, one label per sub-issue by the intake run (generated, not in setup-labels.sh)

    feedback:child-of-<issue> is what lets the pipeline close a parent without ever editing an issue body: after a merge it lists the parent's children and closes the parent only when none are open.

    Prototype feedback loop¶

    maquette (?annotate=1)  ->  click a component  ->  issue labeled prototype-feedback
   ->  opencode-prototype-feedback.yml
        ->  brainstorm panel: designer (UX), product, architect, backend, QA
        ->  synthesis: BR report + one plan per track
        ->  sub-issues UX / FRONTEND / BACKEND, label feedback:child-of-<parent>
   ->  opencode-pipeline.yml, one parallel chain per sub-issue
   ->  parent feedback issue closes when every child is merged
    Stage Actor What happens
    Capture human static annotation layer in the maquette; pre-fills screen, data-uid, CSS path, prototype URL, viewport
    Intake brainstormer (delegated by orchestrator) panel discussion → BR-NNN-*.md (+ ADR when durable)
    Decomposition orchestrator one sub-issue + one PLAN-*.md per affected track; UX → designer, FRONTEND → frontend-implementer, BACKEND → backend-implementer
    Execution per sub-issue the normal implement → qa → review → auto-merge chain, in parallel
    Completion opencode-pipeline.yml parent closed automatically when no child is open

    Properties worth knowing:

    • Trust gate. The prototype is public, so only a prototype-feedback issue whose author is in OC_TRUSTED_ACTORS is executed. Anything else is parked as status:backlog with an explanatory comment. The issue body is untrusted input: the intake reads it through the gh JSON API and never interpolates it into a shell command (AGENTS.md, security rules).
    • No double handling. opencode-issue-triage.yml skips issues carrying prototype-feedback; the intake skips issues already carrying feedback:parent. Both gates are label-driven, so the loop cannot re-trigger.
    • No design ceremony for nits. The intake is told to skip the panel and close the parent directly when the feedback is a copy/colour/label tweak.
    • The pre-fill records the element data-uid, so a new annotatable component needs a data-uid on its structural element. See docs/product/maquette/maquette.md.

    Status markers¶

    Meaningful state changes are posted as standardized comments:

    🤖 STARTED | 🤖 ANALYZING | 🤖 BRAINSTORMING | 🤖 PLANNING | 🤖 IMPLEMENTING
🤖 TESTING | 🤖 REVIEWING | 🤖 BLOCKED | 🤖 COMPLETED

    These are concise; durable analysis lives in docs/ai/brainstorms/ and PRs.

    Run IDs and identity¶

    Every execution has a run ID: run-YYYY-MM-DD-NNNN.

    Where to find a run ID:

    • in the status comments on the Issue/PR,
    • in Git trailers on agent commits,
    • in the PR's AI Execution table,
    • in brainstorm/decision reports,
    • in workflow logs.

    The run ID ties a human request → Issue → agent → model → branch → commits → PR → QA/review → merge. See the audit chain below.

    The audit chain (traceability)¶

    For any task you should be able to answer:

    Question Where to look
    Who requested it? the issue creator / command comment author (github.actor)
    Which Issue? Issue: #N trailers, Closes #N
    Which agent? Agent: <name> trailers/comments, agent:* labels
    Which run? Agent-Run: run-… trailers, status comments
    Which model? the AI Execution table on the PR + .github/oc-models.json
    Which decision? docs/ai/brainstorms/BR-NNN-*.md + ADRs
    Which files changed? the PR diff
    Which branch / commits? the PR
    Which tests? CI run + QA comment evidence
    Which reviewers? review comments + status:review
    Who approved/meged? the PR "merged by" info

    Chain shape:

    Human → Issue #N → Run ID → Brainstorm report → ADR → Branch → Commit(s)
      → PR → QA result → Security result → Human approval → Merge

    GitHub Project (fields)¶

    A GitHub Project v2 can hold status automation. Recommended fields:

    Status, Type, Priority, Domain, Agent, Current Run, Milestone, Risk, AI Decision.

    Automating these fields requires a token that can write the Project (project scope for classic PAT, or a fine-grained token with "Projects" read/write) and org/owner setup — that is intentionally NOT embedded in the workflows or the repo (no credentials in the repository). Set it up manually and connect the Status field to the status:* labels if you want Board integration.

    Human overrides¶

    An explicit human comment always overrides an earlier agent decision. Example:

    Agent: I selected option B.
Human: /oc use option A instead

    The orchestrator records the override, explains impact, updates the plan, and continues with option A.

    Loop protection¶

    Workflows ignore comments/issues authored by bot actors (*[bot]). Moving the state forward is always the human's action; agent comments cannot re-trigger themselves. PRs created by the agent team use GITHUB_TOKEN, so they do not spur new auto-review runs — review is requested explicitly or runs once for human-authored PRs.

    Recovery¶

    If a workflow fails, a model times out, or a partial implementation exists, recover by running opencode-agent-status from the Actions tab (or comment /oc status): the orchestrator inspects existing branches, PRs, comments, run metadata, and CI, then reports current state and the recommended next action instead of duplicating work.

    Required / recommended GitHub setup¶

    • Labels: bash scripts/setup-labels.sh (upsert the standardized label set).
    • Repository variable OC_TRUSTED_ACTORS: CSV of human accounts allowed to run mutation commands, e.g. oussAbd.
    • Secrets (all optional): OPENCODE_API_KEY (OpenCode gateway/team key), provider keys (e.g. ANTHROPIC_API_KEY) if models move off the free gateway.
    • GitHub Project v2 fields: see above (manual).
    • Branch protection on main (requires a paid plan; convention-only otherwise: agents never merge).
