    Brainstorming Report¶

    Metadata¶

    Issue: #9 (https://github.com/share-org/share/issues/9) Date: 2026-09-25 Participants: documentation, architect, security-reviewer, orchestrator Status: DECIDED

    Problem¶

    The docs/ai/mcp-strategy.md document contains a "Recommended permissions by agent" table (lines 45-99) that defines MCP server capabilities per agent. This table appears to conflict with actual agent frontmatter permissions in .opencode/agents/*.md. The issue asks to either label the MCP permissions as "aspirational" or align the frontmatter — but these are fundamentally different permission models operating at different layers.

    Context¶

    • MCP permissions (mcp-strategy.md): Future-facing definitions of what MCP server capabilities agents should have when MCP servers are configured (GitHub, Database, Repository, CI, Production, Web access). The document header states: "No MCP servers are configured during bootstrap. Nothing here invents server names, credentials, or URLs. This document defines intent and permissions for when MCP servers are added."
    • Frontmatter permissions (agent files): Current OpenCode tool permissions controlling what tools agents can use during execution (read, edit, write, bash, webfetch, websearch, task, etc.). These were recently updated per ADR-001 (Issue #5) to follow a consistent least-privilege pattern.
    • BR-001 / ADR-001: Already resolved the OpenCode agent permission architecture. The three problematic agents (qa-engineer, backend-implementer, frontend-implementer) now have restrictive, consistent permission blocks.

    Constraints¶

    • Must not conflate two different permission models
    • Must preserve the aspirational/forward-looking nature of MCP strategy
    • Must not retroactively change ADR-001 decisions
    • Must be clear to future readers/maintainers

    Requirements¶

    • mcp-strategy.md must accurately reflect its purpose (intent for future MCP servers)
    • Agent frontmatter must accurately reflect current OpenCode tool permissions
    • No false equivalence between the two models

    Unknowns / Assumptions¶

    • Assumption: The MCP strategy will eventually be implemented; the table serves as a design target.
    • Unknown: Exact MCP server capabilities when implemented.
    • Unknown: Whether any future MCP server integration will map directly to current frontmatter tools.

    Proposals¶

    Option A: Documentation Agent — Table Note Only¶

    Description: Add an explicit header note above the "Recommended permissions by agent" table stating these are aspirational MCP server capability definitions — not current OpenCode tool permissions.

    Advantages: Minimal change; preserves all existing MCP permission definitions; eliminates false equivalence; honest about aspirational nature.

    Disadvantages: Doesn't remove the table (which some might still find confusing); note might be missed.

    Risks: Low — purely documentation clarification.

    Option B: Architect — Two-Layer Architecture Section¶

    Description: Formally distinguish the two permission layers in the document structure: Layer 1 (OpenCode Tool Permissions, current) and Layer 2 (MCP Server Capabilities, future). Add a "Permission Model Layers" section explaining this distinction.

    Advantages: Architecturally sound separation of concerns; future-proof; prevents category errors in future decisions.

    Disadvantages: More verbose; may be over-engineering for current needs; adds documentation maintenance burden.

    Risks: Medium — adds maintenance surface; premature for pre-implementation docs.

    Option C: Security Reviewer — Explicit "Not Enforced" Label¶

    Description: Label the table explicitly as "Aspirational MCP Capabilities (Not Enforced)" and add a security note referencing ADR-001 as the current enforcement authority.

    Advantages: Security-audit friendly; clear enforcement boundary; reinforces ADR-001 as current authority.

    Disadvantages: "Not Enforced" could be misread as "these don't matter" rather than "future design."

    Risks: Low — improves security clarity; slight risk of discouraging future MCP implementation.

    Option D: Orchestrator — Header Rename + Preamble (SELECTED)¶

    Description: Replace the section header "## Recommended permissions by agent" with "## Aspirational MCP Server Capabilities by Agent (Future)" and add a one-sentence preamble cross-referencing ADR-001 and frontmatter.

    Advantages: Highest leverage (header is most visible); fixes mental model at source; zero maintenance; works for human and agent consumers; audit-friendly.

    Disadvantages: Doesn't add architectural depth (not needed for this fix).

    Risks: Very low — purely a label change.

    Discussion¶

    Key disagreements recorded:

    1. Structural vs. minimal fix: Architect preferred a two-layer architectural explanation; others preferred minimal label fix. Resolution: Minimal fix now; structural docs (ADR) later if MCP implementation proceeds.

    2. "Not Enforced" vs. "Aspirational" framing: Security reviewer favored "Not Enforced" for audit clarity; others preferred "Aspirational... (Future)" as constructive forward-looking framing. Resolution: "Aspirational... (Future)" + "design intent" language — more constructive, still audit-clear.

    3. Table content changes: No participant proposed changing the table content — all agreed it correctly represents future design intent.

    Decision¶

    Selected solution: Option D (Orchestrator) — Header rename + preamble sentence.

    Concrete Changes to docs/ai/mcp-strategy.md¶

    1. Line 45: Change ## Recommended permissions by agent → ## Aspirational MCP Server Capabilities by Agent (Future)

    2. After line 45 (new line 46): Add preamble:

      The following table defines intended MCP server capabilities for each agent when MCP servers are configured. These are NOT current OpenCode tool permissions (defined in agent frontmatter per ADR-001). The two permission models operate independently: frontmatter controls OpenCode tool access during execution; this table expresses design intent for future MCP server integration.

    3. Table content (lines 47-99): Unchanged.

    Why¶

    • Root cause addressed: The ambiguous header "Recommended permissions by agent" is the primary confusion vector. Renaming it fixes the mental model at the highest visibility point.
    • Minimal and surgical: One header change + one sentence. No table edits, no structural reorganization.
    • Audit-friendly: Explicitly references ADR-001 as the current authority, draws clear enforcement boundary.
    • Future-proof: "Aspirational... (Future)" and "design intent" language remains accurate regardless of MCP implementation timeline.
    • Agent-readable: The orchestrator and other agents parsing this document will encounter the clarified header first.

    Trade-offs¶

    Trade-off Decision
    Minimal fix vs. architectural depth Minimal fix now; architectural doc (ADR) later if MCP implementation proceeds
    Explicit "Not Enforced" vs. "Aspirational/Design Intent" "Aspirational... (Future)" + "design intent" — constructive forward-looking framing
    Header-only vs. header + body notes Header + one-sentence preamble strikes the right balance

    Risks¶

    1. Low: Future reader might still confuse the models despite clarification. Mitigation: The preamble explicitly cross-references ADR-001 and frontmatter.
    2. Low: MCP implementation diverges from this table. Mitigation: Table is explicitly labeled "aspirational" and "design intent" — divergence is expected.
    3. None: No runtime behavior changes; purely documentation.

    Rejected Alternatives¶

    Alternative Reason
    Add table note only (Option A) Header remains misleading; note easily missed
    Two-layer architecture section (Option B) Over-engineering for a label confusion; premature for pre-implementation docs
    "Not Enforced" label only (Option C) Could discourage future work; doesn't fix header ambiguity
    Align frontmatter to MCP table Category error — different models, different layers, different purposes
    Delete the table Loses valuable design intent for future MCP work

    Follow-up¶

    • Apply the two changes to docs/ai/mcp-strategy.md
    • No ADR needed — this is a documentation clarification, not an architectural decision
    • If MCP server implementation begins in the future, consider an ADR formalizing the two-layer permission model

    Confidence¶

    HIGH — The problem is a documentation labeling ambiguity between two clearly distinct permission models. The fix is minimal, addresses the root cause (ambiguous header), preserves all design intent, references the authoritative current permission decision (ADR-001), and introduces no runtime risk.
