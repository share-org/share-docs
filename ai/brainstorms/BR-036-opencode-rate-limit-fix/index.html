    Brainstorming Report¶

    Metadata¶

    Issue: #36 Date: 2026-09-27 Participants: orchestrator, architect Status: COMPLETED

    Problem¶

    The anomalyco/opencode/github@latest action starts with an unauthenticated curl to https://api.github.com/repos/anomalyco/opencode/releases/latest to get the latest version. On GitHub-hosted runners (shared IPs), this hits the 60 req/hr unauthenticated rate limit and fails with exit code 22, causing the entire action to abort before installing opencode. All 7 workflows in this repo use this action, so no agent job has ever run successfully.

    Context¶

    • 7 workflows use uses: anomalyco/opencode/github@latest:
    • project-manager-loop.yml (line 189)
    • opencode-pr-review.yml (line 57)
    • opencode-command.yml (lines 160, 214, 286)
    • opencode-pipeline.yml (line 168)
    • opencode-prototype-feedback.yml (line 175)
    • opencode-issue-triage.yml (line 70)
    • opencode-agent-status.yml (line 47)
    • The action exposes NO input to pin or skip the version lookup
    • We cannot modify the upstream action (third-party)
    • The action runs with GITHUB_TOKEN available in env
    • Current fallback version=${VERSION:-latest} never executes because curl -f fails the step first

    Constraints¶

    • Must work for all 7 workflows
    • Must use authenticated GitHub API (with GITHUB_TOKEN) to avoid rate limits
    • Must not require changes to the upstream action
    • Must be a local workaround (composite action or wrapper)
    • Must pin opencode version to avoid the lookup entirely
    • NEVER deploy or touch production
    • NEVER commit secrets

    Requirements¶

    1. Fix the rate limit failure so agent jobs can start
    2. Work reliably on shared GitHub runners
    3. Be maintainable (single place to update opencode version)
    4. Preserve all current action inputs (agent, model, prompt, use_github_token, etc.)
    5. Minimal migration effort across 7 workflows

    Unknowns / Assumptions¶

    • The exact opencode installation method (binary download? npm? script?)
    • Whether the action supports a version input (issue says it doesn't)
    • Current opencode version to pin
    • Whether the action does anything beyond installation (auth setup, config generation)

    Proposals¶

    Option A: Local Composite Action (Architect's Proposal)¶

    Create a local composite action .github/actions/opencode-install that reimplements the opencode installation and execution logic using authenticated GitHub API calls, preserving the exact same input interface as the upstream action. Replace all 7 workflow references from uses: anomalyco/opencode/github@latest to uses: ./.github/actions/opencode-install.

    Description: - New composite action at .github/actions/opencode-install/action.yml - Pins opencode version in the action (e.g., v0.1.23) - Uses GITHUB_TOKEN for authenticated API calls if version lookup ever needed - Implements robust fallback: pinned version → authenticated latest lookup → error - Mirrors all upstream inputs: agent, model, prompt, use_github_token, etc. - Each workflow changes only the uses: line

    Advantages: - Single source of truth for opencode version - Uses authenticated API (avoids 60 req/hr limit) - Preserves all upstream inputs - 7 workflows change only the uses: line — no input restructuring - Composite action runs on runner directly (no container overhead) - Full control over installation logic

    Disadvantages: - We own the installation logic (must track upstream changes) - Need to reverse-engineer how opencode is distributed - Slightly more code to maintain than a wrapper

    Risks: - If opencode changes release artifact structure, our action breaks - If upstream adds new inputs, we must mirror them - Initial implementation requires discovering actual install method

    Option B: Pre-step Version Lookup + Pinned Action Reference¶

    Add a preliminary step in each workflow that fetches the version using authenticated curl with GITHUB_TOKEN, then passes it to the upstream action via a version input (if supported) or uses a pinned action reference like anomalyco/opencode/github@v0.1.23.

    Description: - Each workflow adds a step: Get opencode version (authenticated) - Uses gh api or authenticated curl with GITHUB_TOKEN - Pins the action to a specific version tag - Only works if upstream action accepts version input or we pin the action ref

    Advantages: - Minimal code change (just add step + pin action ref) - No new action to maintain - Authenticated lookup solves rate limit

    Disadvantages: - Issue states upstream action has NO version input - Pinning action ref (@v0.1.23) still runs that version's code, which may have the same unauthenticated curl bug - Must update 7 workflows individually when version changes - Doesn't fix the root cause in the action's code

    Risks: - If pinned action version has the bug, it still fails - Version drift across 7 workflows - Upstream action may not be semantically versioned

    Option C: Fork and Fix Upstream Action¶

    Fork anomalyco/opencode repository, fix the unauthenticated curl (add || true fallback or use authenticated API), publish to our own GitHub account, and reference our fork.

    Description: - Fork the action repo - Fix the version lookup step - Use uses: our-org/opencode/github@latest (or pinned) - Submit PR upstream

    Advantages: - Fixes root cause - Benefits community - Clean separation

    Disadvantages: - Requires maintaining a fork - Upstream may not accept PR - Still need to pin version or trust latest on fork - More operational overhead

    Risks: - Fork diverges from upstream - Security responsibility for forked action - Delay in getting fixes from upstream

    Option D: Wrapper Script Action¶

    Create a simple wrapper that installs opencode via a known method (e.g., npm install -g opencode or download from known URL pattern) and then invokes it, bypassing the upstream action entirely.

    Description: - Composite action that runs npm install -g @opencode/cli@<pinned-version> or similar - Then runs opencode with the provided arguments - No GitHub API calls at all

    Advantages: - Zero GitHub API dependency - Simple, reliable - Version pinned in one place

    Disadvantages: - Assumes npm distribution (may not be how opencode is distributed) - May miss action-specific setup (auth, config, environment) - Need to verify opencode CLI interface matches action expectations

    Risks: - If opencode isn't on npm, this fails - Action may do more than just npx opencode ...

    Discussion¶

    The architect's Option A (local composite action) is the only approach that satisfies ALL constraints simultaneously: 1. ✅ Works for all 7 workflows (single uses: change each) 2. ✅ Uses authenticated API (via GITHUB_TOKEN in composite action) 3. ✅ No upstream changes needed 4. ✅ Local workaround 5. ✅ Pins version in one place 6. ✅ Preserves all inputs (drop-in replacement) 7. ✅ Minimal migration (one line per workflow)

    Option B fails because the upstream action has no version input and pinning the action ref doesn't fix the buggy code inside that version.

    Option C adds operational overhead (maintaining a fork) and doesn't eliminate the need for a local solution if upstream rejects the fix.

    Option D is attractive but risky without knowing opencode's distribution method. The composite action in Option A can START with Option D's approach (direct install) and fall back to authenticated GitHub Releases API if needed.

    Decision¶

    Selected solution: Option A — Local Composite Action

    Why¶

    • Only option meeting all hard constraints
    • Single point of version control
    • Drop-in replacement for all 7 workflows
    • Authenticated API access built-in
    • Extensible for future opencode changes
    • Follows GitHub Actions best practice (local actions for customization)

    Trade-offs¶

    • We own the installation logic (maintenance burden)
    • Must reverse-engineer opencode distribution initially
    • Slight risk if opencode changes distribution method

    Risks¶

    • Mitigated by: Pinning a known-good version initially; adding automated dependabot-like check for new releases
    • Monitored by: Watching upstream releases; testing in a branch before merging

    Rejected Alternatives¶

    • Option B: Upstream action has no version input; pinning ref doesn't fix internal bug
    • Option C: Fork maintenance overhead; upstream acceptance uncertain
    • Option D: Unknown distribution method; may miss action-specific setup

    Follow-up¶

    1. Investigate opencode distribution method (check upstream action source or releases)
    2. Create .github/actions/opencode-install/action.yml composite action
    3. Test with one workflow (e.g., opencode-pr-review.yml)
    4. Migrate remaining 6 workflows
    5. Add version update automation (optional)

    Confidence¶

    HIGH — The constraints leave only one viable path, and composite actions are a well-established GitHub Actions pattern for exactly this use case.
