    Brainstorming Report¶

    Metadata¶

    Issue: #3 (feat EXP-105 : expense shares) Date: 2026-09-22 Participants: backend-implementer, architect, security-reviewer, domain-modeler Status: COMPLETED

    Problem¶

    Implement expense sharing across household members with explicit separation of: who paid, who participated, who owes, allocation method, and how a debt was settled.

    Context¶

    • MVP supports EQUAL and CUSTOM splits (roadmap includes PERCENTAGE and SHARES for Phase 2)
    • Domain model defines: Household, Member, Expense, Money, Allocation, Balance, Settlement
    • Money value object exists with BigDecimal, explicit currency, HALF_UP rounding to 2 decimal places
    • Household isolation is mandatory (security.md)
    • PostgreSQL is the transactional source of truth
    • Modular monolith architecture with domain/application/infrastructure separation

    Constraints¶

    • Never use double/float for monetary values
    • Currency must be explicit
    • Rounding rules must be defined and tested
    • Household isolation: member must not access another household's data by changing identifier
    • Domain must not depend on Spring or database implementation details
    • Keep business logic out of controllers

    Requirements¶

    1. Expense belongs to exactly one household
    2. Payer must be a household member
    3. Participants must be household members
    4. Allocations cannot be negative
    5. Total allocation must equal expense total (with deterministic rounding policy)
    6. Split methods: EQUAL, PERCENTAGE, SHARES, CUSTOM
    7. Audit/history strategy for expense editing

    Unknowns / Assumptions¶

    • Exact rounding policy for allocation remainder distribution
    • Whether allocations are stored as derived values or computed on read
    • API contract shape for creating expenses with different split methods
    • Database schema for expense, allocation, participant relationships
    • How to handle expense editing while preserving audit trail
    • Whether to implement all split methods now or phase them

    Proposals¶

    Option A: Backend Implementer (Implementation-First)¶

    Description: Explicit persisted allocations for all split methods. Strategy pattern in ExpenseAllocationService with HALF_UP rounding, remainder to first N by memberId. Single API endpoint. Database: expense + expense_allocation tables.

    Advantages: Clear separation, testable, extensible, supports audit, simple remainder handling

    Disadvantages: More database rows, allocation service needs careful edge-case testing

    Risks: Rounding edge cases with many participants; service becoming god object

    Option B: Architect (Architecture-First)¶

    Description: Hybrid computed (EQUAL/PERCENTAGE) vs persisted (CUSTOM/SHARES) allocations. Largest remainder (Hamilton) rounding. Separate authorization service. Clean layer separation.

    Advantages: Clean architecture, fair rounding, optimized storage, explicit authorization boundary

    Disadvantages: Hybrid complexity, two code paths, largest remainder harder to implement

    Risks: Inconsistency between computed/persisted; authorization gaps

    Option C: Security Reviewer (Isolation-First)¶

    Description: Application-layer authorization + PostgreSQL RLS as defense-in-depth. Pure domain allocation functions. Event sourcing for audit trail from day one.

    Advantages: Strong isolation, audit built-in, pure domain logic, RLS safety net

    Disadvantages: RLS couples to PostgreSQL, event sourcing overkill for MVP, more infrastructure

    Risks: RLS performance; event table growth; authorization bottleneck

    Option D: Domain Modeler (Domain-First)¶

    Description: Invariants in Expense aggregate. SplitMethod enum with factories. Banker's rounding (HALF_EVEN). Payer receives remainder. Separate BalanceCalculator.

    Advantages: Strong invariants, encapsulated logic, intuitive payer-remainder, clean separation

    Disadvantages: Payer-remainder may seem unfair; HALF_EVEN inconsistent with Money; enum bloat

    Risks: Enum bloat; remainder policy disputes; invariant validation performance

    Discussion¶

    Key disagreements and resolutions:

    1. Persisted vs computed allocations: All specialists except Architect favored uniform persisted allocations. Architect's hybrid approach was rejected due to double code paths, audit complexity, and inconsistency risk. Storage cost is negligible for household scale.

    2. Rounding method: Money class uses HALF_UP. Domain Modeler proposed HALF_EVEN (banker's rounding) but this creates inconsistency. Architect proposed largest remainder (mathematically fair but complex). Consensus: HALF_UP consistently, remainder to first N by deterministic memberId ordering.

    3. Payer-remainder vs first-N remainder: Domain Modeler argued payer should get remainder (intuitive). Others argued this is arbitrary and may confuse users. First-N by memberId is more explainable and testable.

    4. RLS and event sourcing: Security Reviewer advocated for both as defense-in-depth. Others rejected as over-engineering for MVP, coupling domain to PostgreSQL, and YAGNI. Application-layer authorization with AOP is sufficient.

    5. SplitMethod enum factories: Domain Modeler proposed factories on enum. Backend Implementer and Architect argued this bloats the enum; allocation logic belongs in domain service/factory.

    6. Authorization enforcement: Consensus on application-layer checks via HouseholdAuthorizationService + Spring AOP interceptor. Repository methods require householdId parameter. RLS deferred.

    Decision¶

    Selected solution: Uniform persisted allocations with HALF_UP rounding, remainder to first N by memberId, Expense factory encapsulating allocation creation, application-layer authorization with AOP, single API endpoint, deferred RLS/event sourcing.

    Why¶

    1. Persisted allocations uniformly - simplest, supports audit/editing, negligible storage cost
    2. HALF_UP rounding consistently - matches existing Money class, no dual rounding modes
    3. Deterministic remainder distribution - by memberId ordering is explainable and testable
    4. Expense factory encapsulates allocation creation - keeps invariants in aggregate, follows DDD
    5. Application-layer authorization with AOP - clean, testable, no PostgreSQL coupling
    6. Single API endpoint with discriminator - simpler routing, extensible
    7. Deferred event sourcing/RLS - YAGNI for MVP, can add later

    Trade-offs¶

    Decision Trade-off
    Persist all allocations Slightly more rows, but uniform code and audit support
    Remainder to first N by memberId Not "fairest" mathematically, but deterministic and explainable
    Single API endpoint Slightly more complex request validation, but simpler routing
    No RLS/event sourcing Relies on application correctness; mitigated by tests and AOP
    HALF_UP only Consistent with Money; no banker's rounding complexity

    Rejected Alternatives¶

    1. Hybrid computed/persisted allocations - double code paths, audit complexity, inconsistency risk
    2. Largest remainder rounding - harder to explain, more complex implementation
    3. Payer receives remainder - arbitrary, may confuse users
    4. Banker's rounding (HALF_EVEN) - inconsistent with Money class
    5. RLS + Event Sourcing - over-engineering for MVP, couples domain to PostgreSQL
    6. SplitMethod enum factories - bloats enum, allocation logic belongs in domain service/factory

    Risks¶

    1. Rounding edge cases - Mitigation: comprehensive unit tests for all split methods
    2. Authorization gaps - Mitigation: AOP interceptor + repository contract + integration tests
    3. Allocation service complexity - Mitigation: strategy pattern with separate class per split method
    4. Expense editing audit - Mitigation: updated_by/updated_at for MVP; design for future event table

    Open Questions¶

    1. Should ExpenseAllocationService be in domain or application layer? (Currently domain)
    2. How to handle expense deletion? Soft delete (status) or hard delete? (Hard delete with FK cascade for MVP)
    3. Should participantIds be derivable from allocations? (Yes for EQUAL/PERCENTAGE/SHARES; explicit for CUSTOM)

    Confidence¶

    HIGH - Strong alignment across specialists on core decisions. Clear precedent from existing Money class and domain model documentation. Well-understood problem space with bounded scope (MVP: EQUAL + CUSTOM).
