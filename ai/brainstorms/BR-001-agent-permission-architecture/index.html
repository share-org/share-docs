    Brainstorming Report¶

    Metadata¶

    Issue: #5 (https://github.com/share-org/share/issues/5) Date: 2026-09-21 Participants: security-reviewer, backend-implementer, qa-engineer, code-reviewer Status: DECIDED

    Problem¶

    The OpenCode agent permission architecture has two critical inconsistencies identified in the baseline code review (issue #2):

    • C1: .opencode/agents/qa-engineer.md has unrestricted bash: allow — the most dangerous permission in the roster, inconsistent with every other agent (orchestrator, code-reviewer, security-reviewer use git *: allow, *: deny).
    • C2: .opencode/agents/backend-implementer.md and .opencode/agents/frontend-implementer.md have NO permission: block at all — the two write-capable implementation agents are the least constrained and least documented.

    Context¶

    • 11 agents total: 1 primary (orchestrator) + 10 subagents
    • 8 agents already have proper restrictive permissions following a consistent pattern
    • 3 agents are problematic (qa-engineer, backend-implementer, frontend-implementer)
    • Repository is a modular monolith with mandatory household isolation (AGENTS.md)
    • Agents never merge production code automatically
    • AGENTS.md security rules: "Never give database write access to unknown/untrusted clients", "Household isolation is mandatory"

    Constraints¶

    • Must follow least-privilege principle
    • Must be consistent across the roster (follow orchestrator/code-reviewer/security-reviewer pattern)
    • Must not break agent functionality (implementers need to write code, QA needs to run tests)
    • Fix must be minimal and follow existing patterns
    • Valid permission keys per config schema: read, edit, write, glob, grep, list, bash, task, external_directory, todowrite, question, webfetch, websearch, lsp, doom_loop, skill

    Requirements¶

    Agent Functional Needs
    backend-implementer Read/edit/write Java/Spring files, Maven config, run mvn commands, read database migrations
    frontend-implementer Read/edit/write React/TypeScript files in frontend/, run npm/npx commands
    qa-engineer Run tests (Maven, npm), read test results, inspect code — NO write access needed

    Unknowns / Assumptions¶

    • Assumption: Implementers don't need arbitrary shell; only standard build/test commands (mvn *, npm *, npx *)
    • Assumption: task tool not needed (implementers don't delegate in current workflow)
    • Assumption: webfetch/websearch not needed for any of these three agents
    • Unknown: Whether backend may occasionally need to edit files outside src/** (e.g., Docker, scripts) — mitigated by explicit pom.xml allow and extensible pattern

    Proposals¶

    Option A: Security-Reviewer (Strict Path Scoping)¶

    Description: Narrow path allowlists (src/main/java/**, src/test/java/** for backend; frontend/** for frontend); bash restricted to mvn */npm *; QA gets test-only bash (mvn test*, npm test*).

    Advantages: Strongest security posture; minimal attack surface; consistent with review agents.

    Disadvantages: Backend path too narrow (misses src/main/resources, config, new modules); QA bash too restrictive (blocks mvn clean, mvn dependency:tree).

    Risks: Legitimate development workflows blocked; frequent permission updates needed.

    Option B: Backend-Implementer (Broad Permissive)¶

    Description: edit: allow, write: allow for backend; file-type patterns for frontend; bash allowlist for build commands.

    Advantages: Zero friction for legitimate work; simple.

    Disadvantages: Violates least privilege — edit: allow/write: allow with no path restrictions allows modification of agent configs, security docs, frontend code, any file. Inconsistent with roster.

    Risks: HIGH — contradicts AGENTS.md principle applied to agents; security regression.

    Option C: QA-Engineer (File-Type Patterns + Test-Focused)¶

    Description: File-type patterns (**/*.java, **/pom.xml, **/*.yml) for backend; QA has zero write; test-scoped bash allowlist.

    Advantages: QA write-zero is correct; file-type patterns handle new files; test-focused bash.

    Disadvantages: **/*.yml too broad (allows CI/CD, docker-compose); file-type patterns miss non-standard extensions; no sensitive path denies.

    Risks: Medium — accidental modification of infrastructure config.

    Option D: Code-Reviewer (Pattern Consistency + Defense-in-Depth) ← SELECTED BASE¶

    Description: Exact orchestrator pattern (map + *: deny fallback) for all tools; src/** + pom.xml for backend with explicit denies for .opencode/**, docs/architecture/security.md; frontend/** for frontend with same sensitive denies; QA gets mvn */npm * bash; explicit denies for webfetch, websearch, task, skill, external_directory.

    Advantages: Maximum consistency; defense-in-depth; explicit audit trail; follows established convention.

    Disadvantages: Most verbose; sensitive path deny list maintenance.

    Risks: Low — denies are additive safety; can extend allowlist if needed.

    Discussion¶

    Key disagreements recorded:

    1. Backend file scope: Security-Reviewer (narrow src/main/java/**) vs Backend-Implementer (broad edit: allow) vs Code-Reviewer (src/** with sensitive denies) vs QA-Engineer (file-type **/*.java). Resolution: src/** with sensitive denies balances practicality and safety.

    2. QA bash scope: Security-Reviewer/Code-Reviewer (mvn *, npm *) vs QA-Engineer (test-only mvn test*). Resolution: Broader mvn */npm * — QA needs clean, dependency:tree, etc.

    3. Tool exclusions: Only Code-Reviewer proposed explicit webfetch/websearch/task/skill denies. Resolution: Include explicit denies for clarity and audit.

    4. Sensitive path denies: Only Code-Reviewer proposed .opencode/** and docs/architecture/security.md denies. Resolution: Include for defense-in-depth.

    Decision¶

    Selected solution: Refined Option D (Code-Reviewer base with adjustments from critique).

    Concrete Permission Blocks¶

    qa-engineer.md¶

    permission:
  edit: deny
  write: deny
  read: allow
  glob: allow
  grep: allow
  list: allow
  bash:
    "mvn *": allow
    "npm *": allow
    "*": deny
  webfetch: deny
  websearch: deny
  task: deny
  skill: deny
  external_directory: deny

    backend-implementer.md¶

    permission:
  read: allow
  glob: allow
  grep: allow
  list: allow
  edit:
    "src/**": allow
    "pom.xml": allow
    ".opencode/**": deny
    "docs/architecture/security.md": deny
    "*": deny
  write:
    "src/**": allow
    "pom.xml": allow
    ".opencode/**": deny
    "docs/architecture/security.md": deny
    "*": deny
  bash:
    "mvn *": allow
    "*": deny
  webfetch: deny
  websearch: deny
  task: deny
  skill: deny
  external_directory: deny

    frontend-implementer.md¶

    permission:
  read: allow
  glob: allow
  grep: allow
  list: allow
  edit:
    "frontend/**": allow
    ".opencode/**": deny
    "docs/architecture/security.md": deny
    "*": deny
  write:
    "frontend/**": allow
    ".opencode/**": deny
    "docs/architecture/security.md": deny
    "*": deny
  bash:
    "npm *": allow
    "npx *": allow
    "*": deny
  webfetch: deny
  websearch: deny
  task: deny
  skill: deny
  external_directory: deny

    Why¶

    • Consistency: Matches the orchestrator/code-reviewer/security-reviewer pattern exactly (map form with allowlist + *: deny fallback).
    • Least privilege: Each agent gets only what it needs; no unrestricted bash, no broad edit: allow.
    • Defense-in-depth: Explicit denies for sensitive paths (agent configs, security docs) prevent accidental/malicious modification.
    • Explicit tool denies: Clarifies that webfetch/websearch/task/skill/external_directory are not needed.
    • Practical: src/** and frontend/** cover legitimate work including new modules/files; mvn */npm * cover all build/test scenarios.

    Trade-offs¶

    Trade-off Decision
    Verbosity vs. clarity Accept verbosity for clarity and auditability
    src/** breadth vs. narrow src/main/java/** src/** preferred (covers resources, test fixtures, new modules); sensitive denies mitigate risk
    Explicit tool denies vs. implicit Explicit denies for documentation and audit trail
    Sensitive path deny list maintenance Accept maintenance burden for defense-in-depth

    Risks¶

    1. Backend may need files outside src/** (Docker, scripts, root config). Mitigation: pom.xml explicitly allowed; rare cases can extend allowlist.
    2. Build command evolution (wrapper scripts, new npm commands). Mitigation: mvn * covers wrapper; npm * covers all npm.
    3. QA may need non-Maven/npm commands (docker, psql). Mitigation: Not in current scope; extend if needed.

    Rejected Alternatives¶

    Alternative Reason
    Backend-Implementer's edit: allow, write: allow Violates least privilege; inconsistent; security risk
    Security-Reviewer's narrow src/main/java/** Too restrictive; breaks legitimate work (resources, test fixtures)
    QA-Engineer's test-only bash (mvn test*) Too restrictive; QA needs mvn clean, mvn dependency:tree
    Omitting explicit webfetch/websearch/task denies Implicit deny per schema, but explicit is clearer for audit
    File-type patterns (**/*.java) Misses non-standard extensions; directory patterns more maintainable

    Follow-up¶

    • Apply the three permission blocks to their respective agent files
    • Verify agents can still perform their duties (run a test task for each)
    • Consider whether architect and product-planner should get bash: { "git *": allow, "*": deny } for consistency (currently they have no bash at all)

    Confidence¶

    HIGH — The solution follows the established pattern in the repository, applies least privilege consistently, addresses both C1 and C2 findings, and the trade-offs are well-understood. The only uncertainty is whether any edge-case file paths are missed, but the pattern allows easy extension.
