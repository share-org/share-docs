    Implementation Plan: EXP-105 Expense Shares¶

    Issue: #3 Run: run-2026-09-24-0005 Brainstorm: (no brainstorm report created; previous attempts failed) Agent: architect Agent-Run: run-2026-09-24-0005

    Affected areas¶

    Layer Components
    Domain Expense aggregate, SplitMethod enum (add SHARES), Allocation value object, ShareAllocationCalculator domain service, ExpenseRepository port
    Application CreateExpenseUseCase, CreateExpenseCommand, ExpenseNotFoundException, InvalidExpenseException
    Infrastructure (Persistence) ExpenseJpaEntity, ExpenseAllocationJpaEntity, ExpenseRepositoryImpl, ExpenseMapper, Flyway migration V2__expense_shares.sql
    API ExpenseController, CreateExpenseRequest/Response DTOs, ShareAllocationDto, OpenAPI docs
    Security Household membership verification in use case / repository

    Domain changes¶

    1. SplitMethod enum — add SHARES alongside EQUAL, PERCENTAGE, CUSTOM
    2. Allocation value object — add shareCount field (nullable, only for SHARES)
    3. Expense aggregate — validate SHARES-specific invariants:
    4. All participants have shareCount > 0
    5. totalShares = sum(participant.shareCount)
    6. Allocations computed via deterministic formula
    7. ShareAllocationCalculator (new domain service) — pure function: java List<Allocation> calculate(Money total, List<ShareParticipant> participants)
    8. Computes each allocation = total * share / totalShares, rounded HALF_UP (2dp)
    9. Distributes rounding remainder to first participant (deterministic)
    10. Guarantees sum(allocations) == total

    Persistence / migrations¶

    Change Required
    New columns on expense_allocations: share_count (INT, nullable) Yes
    Flyway migration V2__expense_shares.sql Yes
    Index on expense_allocations(expense_id) for N+1 prevention Yes
    No change to expenses table (split_method already exists) —

    Migration strategy: Add share_count nullable; existing EQUAL/CUSTOM rows keep NULL.

    API changes¶

    POST /api/households/{householdId}/expenses

    Request body (extension):

    {
  "description": "Groceries",
  "total": "90.00",
  "currency": "EUR",
  "payerId": "member-uuid",
  "splitMethod": "SHARES",
  "participants": [
    { "memberId": "alice-uuid", "shareCount": 2 },
    { "memberId": "bob-uuid", "shareCount": 1 },
    { "memberId": "charlie-uuid", "shareCount": 1 }
  ],
  "occurredAt": "2026-09-24T12:00:00Z"
}

    Response includes computed allocations:

    {
  "id": "expense-uuid",
  "allocations": [
    { "memberId": "alice-uuid", "amount": "45.00", "shareCount": 2 },
    { "memberId": "bob-uuid", "amount": "22.50", "shareCount": 1 },
    { "memberId": "charlie-uuid", "amount": "22.50", "shareCount": 1 }
  ]
}

    Validation: splitMethod=SHARES requires all participants to have shareCount > 0.

    Ordered implementation steps¶

    1. Domain: SplitMethod enum — add SHARES
    2. Domain: Allocation — add shareCount field + factory method forShares(memberId, amount, shareCount)
    3. Domain: ShareParticipant (value object) — memberId, shareCount
    4. Domain: ShareAllocationCalculator — static calculate(Money, List<ShareParticipant>) with rounding logic + unit tests
    5. Domain: Expense — add createWithShares(...) factory, validate invariants
    6. Domain: ExpenseRepository port — add save(Expense), findById(UUID)
    7. Infrastructure: Flyway migration V2 — add share_count column + index
    8. Infrastructure: ExpenseJpaEntity / ExpenseAllocationJpaEntity — map new field
    9. Infrastructure: ExpenseMapper — map domain ↔ JPA including shareCount
    10. Infrastructure: ExpenseRepositoryImpl — implement port with household-scoped queries
    11. Application: CreateExpenseCommand — include splitMethod, participants (with shareCount)
    12. Application: CreateExpenseUseCase — orchestrate: verify household membership (payer + all participants), delegate to Expense.createWithShares, persist
    13. API: CreateExpenseRequest/Response DTOs — add shareCount to participant DTO
    14. API: ExpenseController — endpoint with validation, householdId from path
    15. OpenAPI — document SHARES split method in schema

    Open questions¶

    1. Rounding remainder recipient: Current plan gives remainder to first participant (by list order). Should it go to payer instead? Domain model doesn't specify — needs product decision.
    2. Share count type: int is sufficient (max ~2B). Confirm no need for long.
    3. API field naming: shareCount vs shares — align with frontend expectations.
    4. Edit expense: Out of scope for this issue; future issue will need audit trail per domain invariant #10.

    Risks¶

    Risk Mitigation
    Rounding errors causing allocation sum ≠ total Exhaustive unit tests with edge cases (1-cent remainders, large share counts)
    Household isolation bypass All repository queries scoped by householdId; integration test verifies cross-household rejection
    N+1 on allocations Fetch expense + allocations in single query (JPA @EntityGraph or native query)
    Migration on non-empty DB share_count nullable; defaults to NULL for existing rows
