    Implementation Plan: HOUSE-002 Invite Member¶

    Issue: #HOUSE-002 Run: run-2026-10-02-0022 Brainstorm: (none — straightforward implementation) Agent: architect Agent-Run: run-2026-10-02-0022

    Affected areas¶

    Domain (com.sharedhousehold.domain.household)¶

    • New Invitation aggregate/entity
    • New InvitationId value object
    • New InvitationStatus enum (PENDING, ACCEPTED, EXPIRED, CANCELLED)
    • New InvitationToken value object
    • New InvitationCreated domain event

    Application (com.sharedhousehold.application)¶

    • New command: InviteMemberCommand
    • New result: InviteMemberResult
    • New use case: InviteMemberUseCase
    • New port: InvitationRepository
    • New exceptions: InvalidInvitationException, MemberAlreadyExistsException, CannotInviteSelfException

    Infrastructure (com.sharedhousehold.infrastructure.persistence)¶

    • New JPA entity: InvitationJpaEntity
    • New Spring Data repository: InvitationJpaRepository
    • New repository implementation: InvitationRepositoryImpl
    • Flyway migration: V6__invitations.sql
    • Configuration: wire InviteMemberUseCase in ApplicationConfig

    API (com.sharedhousehold.api.household)¶

    • New controller endpoint: POST /api/households/{householdId}/invitations
    • Request DTO: CreateInvitationRequest
    • Response DTO: CreateInvitationResponse
    • Validation annotations

    Domain changes¶

    Element Description
    InvitationId UUID-based value object, similar to HouseholdId
    InvitationToken Secure random token value object (URL-safe, ~32 chars)
    InvitationStatus Enum: PENDING, ACCEPTED, EXPIRED, CANCELLED
    Invitation Aggregate root with: id, householdId, invitedEmail, invitedBy (memberId), role, token, status, createdAt, expiresAt, acceptedAt
    InvitationCreated Domain event published when invitation is created

    Invariants: - Invitation token must be unique - Invitation expires after configurable TTL (default 7 days) - Cannot create invitation for email already a member of household - Cannot invite self (invitedBy memberId == invited member's userId, if user exists) - Only household members (any role) can create invitations

    Persistence / migrations¶

    New table: invitations¶

    CREATE TABLE invitations (
    id UUID PRIMARY KEY,
    household_id UUID NOT NULL REFERENCES households(id) ON DELETE CASCADE,
    invited_email VARCHAR(255) NOT NULL,
    invited_by UUID NOT NULL REFERENCES members(id) ON DELETE RESTRICT,
    role VARCHAR(20) NOT NULL DEFAULT 'MEMBER',
    token VARCHAR(64) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP WITH TIME ZONE NOT NULL,
    accepted_at TIMESTAMP WITH TIME ZONE
);

CREATE INDEX idx_invitations_household_id ON invitations (household_id);
CREATE INDEX idx_invitations_token ON invitations (token);
CREATE INDEX idx_invitations_status ON invitations (status);
CREATE INDEX idx_invitations_invited_email ON invitations (invited_email);

    API changes¶

    Endpoint¶

    POST /api/households/{householdId}/invitations

    Request DTO¶

    public record CreateInvitationRequest(
    @Email @NotBlank String invitedEmail,
    @NotNull MemberRole role
) {}

    Response DTO¶

    public record CreateInvitationResponse(
    UUID invitationId,
    UUID householdId,
    String invitedEmail,
    MemberRole role,
    String token,           // only returned once for logging/testing
    Instant expiresAt,
    Instant createdAt
) {}

    Error responses¶

    • 400 - Invalid request (validation)
    • 401 - Unauthorized
    • 403 - Requester not a member of household
    • 404 - Household not found
    • 409 - Email already a member / cannot invite self

    Validation¶

    • householdId path variable: valid UUID
    • invitedEmail: valid email format, not blank
    • role: MEMBER or ADMIN (not OWNER)

    Open questions¶

    1. Email sending: Issue says "email sent (or logged for now)". Should we implement a placeholder EmailService port/adapter now, or just log the token? Recommendation: log for now, add EmailService port in a follow-up.

    2. Token exposure in response: The token is returned in the response for the inviter to share. Is this acceptable, or should the token only be sent via email? Current plan: return token in response (for testing/manual sharing), document that production should use email.

    3. Invitation acceptance flow: Not in scope for this issue (Phase 1). Should we design the acceptance endpoint now? Recommendation: defer to separate issue (HOUSE-003).

    4. Configurable TTL: Where to store default? application.yml with invitation.ttl.days=7. Any need for per-household configuration? Recommendation: global config for now.

    5. Role validation: Should ADMIN role be allowed? Issue says MEMBER/ADMIN. OWNER should be rejected. Confirm this is correct.

    6. Duplicate invitation handling: If an invitation already exists for same email+household and is PENDING, should we return existing or create new? Recommendation: return 409 conflict, let inviter cancel first.

    7. Household isolation verification: The use case must verify the authenticated user (via CurrentUser) is a member of the target household. This requires joining User → Member (by email?) or storing userId on Member. Currently Member doesn't have userId. How to link?

    8. Option A: Add userId to Member (nullable, for registered users)
    9. Option B: Look up member by email matching authenticated user's email
    10. Recommendation: Option B for now (simpler, matches existing pattern where member email = user email). We'll need to add findByHouseholdIdAndEmail to MemberRepository/MemberJpaRepository.

    Risks¶

    Risk Impact Mitigation
    Member-user linkage missing Cannot verify inviter is household member Add findByHouseholdIdAndEmail to MemberRepository; use CurrentUser's email via UserRepository
    Token collision Security issue Use secure random (256-bit), URL-safe base64, check uniqueness in DB
    Invitation enumeration Privacy leak Token is 32+ chars, unguessable; no list endpoint for non-members
    Expired invitations cleanup Data growth Add scheduled cleanup job later; not critical for MVP
    Race condition: duplicate invitation Two invites sent simultaneously DB unique constraint on (household_id, invited_email, status='PENDING') or handle in use case with optimistic locking
