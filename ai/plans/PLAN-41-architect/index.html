    Architect Implementation Plan: HOUSE-001 Create Household¶

    1. Specification Readiness Assessment¶

    The specification at docs/ai/plans/PLAN-41-household-create.md is complete and implementation-ready. It correctly follows the established patterns in the codebase:

    • ✅ Domain layer follows Expense aggregate pattern (factory create, reconstruct, private constructor, immutability)
    • ✅ Application layer uses ports (HouseholdRepository, extended MemberRepository) with no Spring dependencies
    • ✅ Infrastructure uses Spring Data JPA adapters with mapper pattern (HouseholdMapper, MemberRepositoryImpl)
    • ✅ API layer uses explicit DTOs (CreateHouseholdRequest, CreateHouseholdResponse) — no persistence entities exposed
    • ✅ Household isolation enforced server-side (generated IDs, no client-supplied household ID)
    • ✅ Test strategy covers all layers (domain unit, application mocked, integration, API)
    • ✅ Flyway migration V3 adds role column correctly with data migration for existing rows

    2. Technical Risks & Decisions¶

    Risk/Decision Assessment Resolution
    Member role in domain vs. application Spec defines HouseholdMember in domain with role, but Member port record lacks role Correct: role is a domain concern within HouseholdMember entity; application Member record remains lean (used for membership verification only). Adapter maps role at persistence boundary.
    MemberRepository.save() signature Spec adds save(Member) to port, but Member record has no role Adapter MemberRepositoryImpl.save() accepts Member and persists with role default (MEMBER); use case overrides for OWNER via JPA entity constructor. Acceptable for MVP.
    Event publication Direct via ApplicationEventPublisher (synchronous) Acceptable for MVP. Outbox pattern can be introduced later via ADR.
    Email format validation Spec suggests @Email on API DTO only Correct: domain shouldn't know email format rules. API validation suffices.
    Member ID generation Random UUID in use case Matches existing pattern (Expense uses UUID.randomUUID()). Deterministic IDs not needed without auth.
    Rollback safety of V3 migration Adds role column with DEFAULT 'MEMBER' and backfills Safe: ALTER TABLE ... ADD COLUMN ... DEFAULT is metadata-only in PG 11+. Backfill UPDATE is idempotent. Rollback = DROP COLUMN role.

    3. Implementation Sequence (Follows Spec Section 8)¶

    Phase 1: Domain Layer (domain/household/)¶

    1. HouseholdId.java — value object wrapping UUID with generate() / of()
    2. MemberRole.java — enum OWNER, MEMBER
    3. HouseholdMember.java — entity with createOwner() / createMember() factories
    4. Household.java — aggregate root with create() / reconstruct(), invariants (name not blank, ≤255)
    5. HouseholdEvent.java (sealed interface) + HouseholdCreated.java + MemberAdded.java (records)

    Phase 2: Application Layer¶

    1. application/port/household/HouseholdRepository.java — port interface
    2. application/command/household/CreateHouseholdCommand.java — validated record
    3. application/command/household/CreateHouseholdResult.java — result record
    4. application/exception/household/InvalidHouseholdException.java
    5. application/usecase/household/CreateHouseholdUseCase.java — @Service @Transactional, orchestrates household + member creation, publishes events
    6. Update application/port/MemberRepository.java — add Member save(Member member);

    Phase 3: Infrastructure Layer¶

    1. resources/db/migration/V3__household_and_members.sql — add role column, index, backfill
    2. infrastructure/persistence/household/HouseholdJpaEntity.java
    3. infrastructure/persistence/household/HouseholdJpaRepository.java
    4. infrastructure/persistence/household/HouseholdMapper.java — static methods toJpaEntity / toDomain
    5. infrastructure/persistence/household/HouseholdRepositoryImpl.java — implements port
    6. Update infrastructure/persistence/MemberJpaEntity.java — add role field, constructor, getter/setter
    7. Update infrastructure/persistence/MemberJpaRepository.java — add findByHouseholdIdAndRole
    8. Update infrastructure/persistence/MemberRepositoryImpl.java — implement save(Member) with role support

    Phase 4: API Layer¶

    1. api/household/CreateHouseholdRequest.java — @NotBlank @Size(max=255) + @Email on creatorEmail
    2. api/household/CreateHouseholdResponse.java — response DTO
    3. api/household/HouseholdController.java — @PostMapping("/api/households"), maps request→command, result→response, exception handlers

    Phase 5: Tests¶

    1. Domain: HouseholdTest.java, HouseholdIdTest.java, HouseholdMemberTest.java
    2. Application: CreateHouseholdUseCaseTest.java (mocked repos + event publisher)
    3. Integration: HouseholdRepositoryImplTest.java (@DataJpaTest)
    4. Integration: MemberRepositoryImplTest.java — extend existing or new file for role tests
    5. API: HouseholdControllerTest.java (@SpringBootTest @AutoConfigureMockMvc @ActiveProfiles("test") @EnableAutoConfiguration(exclude=SecurityAutoConfiguration.class))

    4. Cross-Cutting Concerns¶

    Transactions¶

    • CreateHouseholdUseCase annotated @Transactional — household + member persist in same transaction
    • If member save fails, household rolls back automatically
    • Events published after successful persistence (within same transaction context)

    Error Handling¶

    • Domain validation throws IllegalArgumentException / NullPointerException → caught in controller as 400
    • InvalidHouseholdException for business rule violations → 400
    • Future: 409 for email conflicts when auth added

    Household Isolation (Security)¶

    • No household ID in create request — generated server-side
    • Creator member ID generated server-side
    • All JPA queries filter by household_id (enforced by MemberJpaRepository methods)
    • No SecurityAutoConfiguration in tests (consistent with existing expense tests)

    Database Migration¶

    • V3 is additive only (new column with default, index, backfill)
    • No breaking changes to existing tables
    • Rollback: DROP COLUMN role + DROP INDEX idx_members_household_id_role

    5. Definition of Done¶

    Criterion Verification
    All domain unit tests pass ./mvnw test -Dtest=HouseholdTest,HouseholdIdTest,HouseholdMemberTest
    Application use case tests pass (mocked) ./mvnw test -Dtest=CreateHouseholdUseCaseTest
    Persistence integration tests pass ./mvnw test -Dtest=HouseholdRepositoryImplTest,MemberRepositoryImplTest
    API tests pass ./mvnw test -Dtest=HouseholdControllerTest
    Full test suite passes ./mvnw test
    Flyway migration applies cleanly ./mvnw flyway:migrate on test DB
    OpenAPI docs generated ./mvnw spring-boot:run → GET /v3/api-docs includes /api/households
    No persistence entities in API layer Code review — only DTOs in api/household/
    No Spring imports in domain Code review — domain/household/ has zero Spring annotations

    6. Notes for Backend Implementer¶

    • Follow the exact package structure in the spec (com.sharedhousehold.domain.household, com.sharedhousehold.application.port.household, etc.)
    • Use @Component on mappers (as HouseholdMapper), @Repository on adapters
    • Reuse Money, SplitMethod patterns for validation style (fail-fast with Objects.requireNonNull, descriptive messages)
    • For HouseholdId, mirror the pattern if a generic Identifier<T> exists — but none exists yet; simple UUID wrapper is fine
    • Keep HouseholdMember in domain; do not leak into application port
    • When updating MemberRepositoryImpl.save(), use the new MemberJpaEntity constructor with role parameter for OWNER case
    • Run ./mvnw test after each phase to catch wiring issues early

    Status: Ready for implementation. No blockers. No ADR required.
