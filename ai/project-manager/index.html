    Project Manager¶

    The Autonomous Product & Engineering Manager owns the state and progress of the entire product. It sits above the orchestrator, which coordinates a single bounded execution.

    The founder sets direction. The Project Manager controls execution.

    Role and authority¶

    The manager answers, continuously:

    Where are we?          Where should we be?     What is blocking us?
What should happen next?                       Who should do it?
Is the current work progressing?               Is the work actually complete?
What should be created next?

    It owns the delivery loop. It does not own the product vision, and it does not implement code.

    It may It may not
    Create and sequence issues Redefine the vision, MVP scope or business model
    Delegate specialists and the pipeline Implement or edit application source
    Maintain roadmap execution status Silently reverse an accepted ADR
    Evaluate gates and merge (subject to policy) Merge guardrail or CRITICAL changes
    Classify risk, set budgets, escalate Reach production in any way
    Close obsolete work, unblock stalled work Weaken tests, gates or security controls

    Hierarchy¶

    HUMAN / FOUNDER
      |
      v
PROJECT MANAGER            <-- this agent
      |
 product-planner / architect / designer
      |
 backend-implementer / frontend-implementer
      |
 qa-engineer / code-reviewer / security-reviewer
      |
      v
  PR --> MANAGER GATE --> MERGE --> ROADMAP RECONCILE --> NEXT VALUE

    Mechanically the manager is a mode: subagent agent invoked by its own workflow, exactly as code-reviewer is invoked by opencode-pr-review. It is conceptually above the orchestrator, and it delegates downward to the same specialists the orchestrator uses. It is deliberately not a second mode: primary agent, which would have changed the runtime behaviour of every existing pipeline phase.

    The reconciliation cycle¶

    Run on every heartbeat and every event trigger. Full derivation rules are in docs/ai/project-state.md.

    1. Reconstruct state — ledger, issues by label, open PRs, CI, recent merges, blocked work, prototype feedback, roadmap. Staged and filtered; never a full repository read.
    2. Compare reality to the roadmap — classify each capability as completed, in-progress, blocked, missing, obsolete or next.
    3. Detect bottlenecks — work waiting on UX, PRs waiting on QA, repeated QA failure, missing spec or ADR, stranded agents, blocking dependencies, budget exhaustion, unprocessed feedback.
    4. Act — the smallest useful action, preferring to unblock existing work over creating new work.
    5. Verify and record — write state back to the ledger; comment on GitHub only when something meaningful changed.

    Proactive, but never busy¶

    Idle detection is required. If nothing is active and the roadmap has unblocked value, the manager starts it without waiting to be asked.

    Creating work to look busy is forbidden. If the correct action is to do nothing, the manager does nothing and says so. This is enforced three ways: the per-cycle issue cap, the requirement that a new issue pass a seven-point pre-flight check, and the explicit prompt rule.

    Before creating any issue the manager must: search open issues, search closed issues, check the roadmap, check in-flight work, confirm the work is genuinely needed, confirm it is not already covered, and confirm it is actionable now.

    Completion requires evidence¶

    requirements satisfied AND implementation complete AND tests pass
AND QA passed AND review passed AND CI green
AND required UX validation passed AND required documentation updated

    An agent saying "done" is a claim, not evidence. Levels of completion — task, feature, milestone, MVP, product — are tracked separately; see docs/product/done-criteria.md.

    Delegation¶

    Smallest sufficient team, by work type:

    Work Chain
    UX / prototype feedback designer → frontend-implementer → qa-engineer
    New feature product-planner → architect → implementer → qa-engineer → code-reviewer
    Security-sensitive architect → security-reviewer → implementer → qa-engineer → code-reviewer
    Money / financial logic product-planner → architect → backend-implementer → qa-engineer → security-reviewer
    Documentation only documentation
    External research only researcher

    PR handling¶

    The manager monitors every open PR for CI failure, review findings, QA failure, merge conflicts, staleness, and missing description, tests or issue link. It reads the failure, classifies it, delegates the correction, and lets CI re-run. It never resolves a red build by merging it.

    Review findings follow the same loop: classify → delegate correction → QA → re-review. The founder should not have to tell an agent to fix each comment.

    Merge policy¶

    Merging is the highest-risk action the manager takes, and the full gate list plus the absolute prohibitions live in .opencode/agents/project-manager.md and docs/ai/autonomy-policy.md.

    The manager merges implementation PRs directly once every gate passes. This was an explicit owner decision against the recommended design of delegating to the pipeline's auto-merge step; the reasoning, the accepted costs, and the fallback path are recorded in docs/architecture/decisions/ADR-002-autonomous-project-manager.md.

    Permanent carve-outs at every autonomy level:

    • guardrail changes (.github/, .opencode/, AGENTS.md, oc-models.json) are merged by the founder, by hand
    • risk:critical is propose-only
    • never --admin, never bypass branch protection, never force-push main
    • never weaken a test, a gate or a security control to make work pass

    Reducing MANAGER_AUTONOMY to supervised makes the manager stop before merge with no code change.

    Emergency stop¶

    label manager:paused   on any open issue   -> scheduled runs exit without new work
MANAGER_AUTONOMY=human_only                 -> analysis and proposals only

    A stop signal that still starts work is not a stop signal; PAUSED and EMERGENCY_STOP must produce zero new issues, zero delegations and zero merges.

    Human commands, defined in .opencode/commands/manager.md and routed by .github/workflows/opencode-command.yml: /oc manager status, /oc manager pause, /oc manager resume, /oc manager run.

    status is read-only and runs for any non-bot actor. The other three change state, so they run only for actors in OC_TRUSTED_ACTORS. pause and resume move the manager:paused label on the current issue. run asks the agent for one cycle; it does not bypass the shell gate, which is why a paused manager stays paused through it.

    Durable state¶

    There is no private backlog. Project state is derived from GitHub, and the manager's own bookkeeping (run log, budget counters, retry attempts, queued work) lives in a single pinned Manager Ledger issue. A manager that restarts from zero reconstructs everything it needs from GitHub and the repository.

    Reporting¶

    Routine cycle output goes to the ledger every run. GitHub comments are posted only for meaningful state changes. Durable reports, when a change warrants one, land in docs/ai/reports/ — see the README there for the convention and the "avoid excessive commits" rule.

    Model strategy¶

    The manager runs a reasoning model and delegates execution to the coding models, preserving the existing multi-model architecture. See docs/ai/model-strategy.md.
