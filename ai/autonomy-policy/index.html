    Autonomy Policy¶

    How much the Project Manager may do without asking the founder. This document is the normative reference; the agent prompt implements it and scripts/test-project-manager.sh pins its safety clauses.

    The founder is always the product authority and always the safety boundary. No autonomy level permits the manager to redefine the business vision, reach production, or merge a guardrail change.

    Configuration¶

    Autonomy is a repository variable, not a code change:

    MANAGER_AUTONOMY = human_only | supervised | autonomous

    Default: supervised.

    It is deliberately independent of the existing AUTOPILOT variable, which governs the pre-existing pipeline. The two must not be conflated: AUTOPILOT=on means "trusted issues flow through the pipeline automatically". It does not grant the manager merge authority. Raising the manager's power is a separate, explicit act.

    To change it:

    gh variable set MANAGER_AUTONOMY --body autonomous

    Modes¶

    human_only¶

    Analyse and propose. Create no issues, change no labels, delegate no agents, merge nothing. Useful for auditing what the manager would do before letting it act.

    supervised — default¶

    Run the full delivery loop: reconcile, create issues, delegate specialists, drive the pipeline through QA and review, open PRs, maintain the ledger and roadmap status.

    Stops before merging. Implementation PRs are left for the founder to merge.

    This is the recommended steady state. It captures most of the value — sequencing, proactive work, unblocking, stalled-PR detection — while keeping the single highest-risk action (an ungated merge) human.

    autonomous¶

    Everything in supervised, plus merging implementation PRs when every gate in the merge policy passes.

    Two carve-outs are permanent and apply at every level, including autonomous:

    • Guardrail changes are never merged by the manager. Any PR touching .github/, .opencode/, AGENTS.md or oc-models.json is merged by the founder by hand.
    • CRITICAL risk (risk:critical) is propose-only. Never implemented, never merged.

    A third prohibition is not a carve-out but an invariant of the merge path: the manager never uses --admin, never bypasses branch protection, and never force-pushes main. If branch protection refuses a merge, that refusal is correct behaviour — the manager stops and escalates.

    Operating states¶

    Separate from the mode, and checked at the start of every run:

    State Behaviour
    NORMAL Proceed per the configured mode.
    PAUSED Set by the manager:paused label on any open issue. Analyse state and report it. Start no new work.
    EMERGENCY_STOP MANAGER_AUTONOMY=human_only. Start nothing at all. Report and exit.

    A stop signal that still starts work is not a stop signal. PAUSED and EMERGENCY_STOP must produce zero new issues, zero new delegations and zero merges.

    Risk classes¶

    Every change is classified before implementation is delegated. The class decides the gates.

    Class Typical changes Handling
    LOW documentation, copy, a simple UI adjustment, an isolated test, a safe refactor may proceed autonomously in any mode
    MEDIUM an ordinary application feature, an additive API change, a database migration with a tested rollback proceeds automatically through the normal QA + review gates
    HIGH authentication, authorization, payment or money logic, a major migration, an architecture change, a data migration, an external integration requires an explicit security-reviewer pass, and is never auto-merged without one
    CRITICAL production infrastructure, a destructive migration, a security-boundary change, secrets, production data modification propose only. Never implement, never merge. Escalate to the founder with status:blocked and evidence.

    Classification is not a formality. "We only changed a query" is how a money bug gets shipped. When genuinely unsure between two classes, take the higher one.

    Financial domain¶

    This application handles money. The following are HIGH or above by default:

    currency   rounding   allocations   balances   settlements   transaction history

    Additional standing rules for the manager:

    • Never allow a test, validation, invariant or rounding rule around a financial calculation to be weakened, skipped, deleted, or marked tolerated in order to make something pass.
    • Never accept "close enough" arithmetic. Exact decimal arithmetic with explicit scale and explicit, tested rounding is the standard; double or float for money is never acceptable.
    • If a money change cannot be made correct, that is a status:blocked with evidence — not a shippable approximation.

    What always requires the founder¶

    Regardless of mode:

    • changing the product vision, MVP scope or business model
    • removing a major feature
    • a destructive data operation
    • a production security-boundary change
    • an irreversible architecture decision
    • a decision with significant infrastructure cost
    • any production access of any kind

    Human override¶

    A human comment always beats an earlier manager decision. On override the manager must record the decision, stop conflicting work, update the issue, plan and roadmap status, and continue with the founder's choice. It must not re-litigate the point in a later cycle.

    See docs/architecture/decisions/ADR-002-autonomous-project-manager.md for the rationale, and in particular for the recorded decision that the manager merges directly rather than delegating to the pipeline.
