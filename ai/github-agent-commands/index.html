    GitHub Agent Commands¶

    The human owner drives the agent team from GitHub. Comment on an Issue or PR with a command starting with /oc (the /opencode alias also works). OpenCode runs inside GitHub Actions using the repository's configured agents and models.

    Command list¶

    Command Group What it does Changes code?
    /oc analyze <topic> analysis Reads the issue/thread and posts an analysis no
    /oc brainstorm <topic> planning Runs collaborative brainstorming, writes docs/ai/brainstorms/BR-NNN-*.md, posts a summary comment writes reports
    /oc plan <feature> planning Writes docs/ai/plans/PLAN-*.md, opens a plan PR no
    /oc implement implementation Verifies readiness, creates a branch, implements, tests, opens/updates a PR yes
    /oc review review Independent code review of the current change/PR no
    /oc qa [criteria] QA Verifies acceptance criteria with test evidence (PASS/FAIL/BLOCKED) no (tests only)
    /oc decide <options> decision Evaluates alternatives and records a decision writes decisions
    /oc continue control Resumes the last approved flow depends
    /oc stop control Halts current work, marks status:blocked no
    /oc explain <topic> read-only Explains an issue, a decision, or a design no
    /oc investigate <topic> read-only Investigates and reports findings no
    /oc status read-only Reports current state and recovery status no

    Targeting an agent¶

    Prefix with @<agent> to direct the work to one logical agent. The orchestrator delegates to the named agent.

    /oc @architect analyze the persistence options
/oc @qa verify the acceptance criteria
/oc @security review authorization
/oc @backend explain the Money rounding rule

    Valid agent names:

    orchestrator, brainstormer, product-planner, architect, backend-implementer, frontend-implementer, qa-engineer, code-reviewer, security-reviewer, documentation, researcher.

    Read-only vs. modifying commands¶

    • Read-only (explain, investigate, status): run for any non-bot actor, with minimal permissions. Good for public discussions.
    • Modifying (analyze, brainstorm, plan, decide, implement, review, qa, continue, stop): only run for trusted actors* listed in the repository variable OC_TRUSTED_ACTORS. An untrusted request is rejected with a comment.

    > analyze, review, qa can write reports/decisions or test artifacts, so they are treated as modifying for permission purposes.

    Trigger phrases are case-insensitive (/OC, Oc are fine).

    Natural language is preserved¶

    Everything after the command is kept. The agents read the full issue thread (description + all comments), so you do not need to restate the requirement.

    /oc implement but use the simpler approach discussed by QA

    The orchestrator receives the Issue, relevant comments, brainstorm report, decision, and your command. Your latest explicit instruction wins.

    Typical lifecycles¶

    Feature:

    1. Create the Issue (product description, acceptance criteria if you have them).
2. (optional) /oc analyze this issue
3. Wait for triage; the team brainstorms + posts a plan, marks status:ready.
4. /oc implement
5. OpenCode opens a PR; review it in the Files tab.
6. /oc qa, then /oc review (or reply to the auto-review)
7. Fix requests: "please address reviewer finding 2 in the PR", or /oc continue
8. Merge in the GitHub UI.

    Reopen/recover:

    /oc status            → what is happening? what should happen next?
/oc continue          → resume after a partial failure
/oc stop              → I want this paused right now

    Decision override:

    Human: /oc use option A instead

    What you see¶

    • Status comments (🤖 STARTED, 🤖 COMPLETED, phase markers) on the Issue.
    • Concise agent comments with identity (Agent:, Run:).
    • Links to durable reports (docs/ai/brainstorms/, ADRs) instead of huge transcripts.
    • Commits carrying Agent: / Agent-Run: / Issue: trailers.
    • PRs with a Summary, Closes #N, AI Execution table, and Review status.
    • CI checks running mvn verify.

    Autopilot mode¶

    When the repository variable AUTOPILOT == 'on', issues opened by trusted actors (in OC_TRUSTED_ACTORS) run the full chain without per-phase /oc commands — the opencode-pipeline.yml workflow self-dispatches each phase:

    issue opened -> analyze (+brainstorm+plan) -> implement -> qa -> review+security
                     -> ready for human merge (you merge)
    • Each phase posts a status comment and advances the status:* labels.
    • status:blocked (or /oc stop) halts the chain; a human comment always overrides.
    • You still merge the PR — the agent team never merges by itself.
    • Manual activation: gh variable set AUTOPILOT --body on -R share-org/share (or the repo Settings → Secrets and variables → Variables UI).
    • Manual one-phase dispatch (e.g. after a fix): gh workflow run opencode-pipeline.yml -f issue=<N> -f phase=<phase> -R share-org/share.

    Notes¶

    • Do not paste instructions meant to bypass the trust model; commands are validated against OC_TRUSTED_ACTORS, not comment text.
    • Comments are not terminal transcripts: keep the thread concise; agents link to reports instead of dumping logs.
    • If a command seems to have done nothing, check the Actions tab for the workflow run, or run /oc status.
