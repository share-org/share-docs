    ADR-002: Autonomous Product & Engineering Manager¶

    Status¶

    Accepted

    Context¶

    The agent suite had a well-defined delivery pipeline but no owner of product-level state. The orchestrator coordinates one bounded execution (analyze → implement → QA → review) for a single issue. Nothing in the system:

    • decided what the next piece of work should be;
    • noticed that the roadmap had moved past what the issues described;
    • noticed a PR had been sitting in review for three days, or that an agent had failed and left an issue stranded with no owner;
    • created follow-up work when an implementation PR revealed a missing prerequisite;
    • distinguished "an agent said done" from "the feature is verifiably complete";
    • kept a durable record of why a piece of work exists and what it unblocks.

    This was already causing observable drift. docs/product/roadmap.md carried no execution status at all, so the intended sequence existed only as prose, and the autonomy pipeline had begun producing stacked PRs on agent branches with no component reasoning about dependency order.

    A top-level manager was requested to close that gap, with the founder retaining product vision and remaining the safety boundary.

    Decision¶

    1. Add project-manager (.opencode/agents/project-manager.md), the Autonomous Product & Engineering Manager, positioned above the orchestrator. It owns delivery state, sequencing, and progress. It does not own product vision and it does not implement code.

    2. GitHub remains the only durable state. The manager reconstructs project state from issues, PRs, labels, CI, ADRs and repository documents on every cycle. Durable manager bookkeeping (run log, budget counters, retry attempts) lives in a single pinned Manager Ledger issue, precisely so that no state exists only in model context.

    3. GitHub labels are authoritative for actual work state. docs/product/roadmap.md gains an execution-status column that the manager mirrors; if the two disagree, labels win.

    4. Autonomy is a separate dial. A new MANAGER_AUTONOMY repository variable (human_only | supervised | autonomous, default supervised) governs the manager, deliberately independent of the existing AUTOPILOT switch. The manager's power can therefore be raised or lowered without changing how the existing pipeline behaves, and the manager cannot gain authority merely because AUTOPILOT happens to be on.

    5. Event-driven execution plus a scheduled heartbeat, not a long-running process. GitHub Actions remains the only runtime.

    6. Risk classes (LOW/MEDIUM/HIGH/CRITICAL) determine which gates apply. CRITICAL is propose-only, always. Money, currency, rounding, allocations, balances and settlements are HIGH or above by default, and financial validation may never be weakened to make work pass.

    7. Bounded, budgeted action. Per-cycle issue caps, PR-in-flight caps and bounded retries, so the loop degrades gracefully instead of running away. A pause/emergency-stop path exists and must be able to start no new work.

    The merge decision, recorded as an explicit override¶

    The recommended design was that the manager never merges and instead delegates merging to the existing pipeline's auto-merge step, which already enforces the QA/review/guardrail gates. The owner reviewed this and chose the opposite: the manager merges implementation PRs directly after evaluating the gates.

    Concretely, the manager runs an ordinary gh pr merge --squash under normal branch protection, as the same automation identity. That ordinaryness is the point: there is no privileged merge path, so branch protection has the final say in every case.

    This is recorded here because it is the highest-risk element of the design and it was a deliberate choice against advice. The known costs:

    • A second merge path now exists. Every gate the pipeline enforces must be re-implemented correctly in the manager, and the two can drift apart.
    • The manager runs under the same GitHub identity (GITHUB_TOKEN) as the agents that author the PRs it would merge, so GitHub branch protection may refuse the merge. That refusal is a fail-safe and must be respected.
    • A bug in the manager's gate evaluation becomes an ungated merge, which is strictly worse than a missing merge.

    Compensating controls, all mandatory:

    • The manager must never use --admin, never bypass branch protection, and never force-push main. If protection blocks it, it stops and escalates.
    • Guardrail changes are never merged by the manager. Any PR touching .github/, .opencode/, AGENTS.md or oc-models.json goes to the founder, by hand, always. This preserves the existing guardrail exemption and stops the suite from rewriting its own constraints.
    • CRITICAL-risk changes are propose-only and never merged.
    • The gate list is pinned by an executable test (scripts/test-project-manager.sh) that fails if a required gate string or prohibition is removed from the agent contract, and is mutation-checked to prove it can actually fail.
    • The founder can reduce the manager to supervised (stop before merge) or human_only at any time with a single variable, without a code change.

    If the second merge path is ever observed to be a problem in practice, the fallback is to revert decision 7's merge clause to delegation; the rest of the manager is unaffected.

    Alternatives considered¶

    1. Extend the existing orchestrator instead of adding an agent. Rejected: the orchestrator's contract is explicitly scoped to one bounded task, runs as mode: primary, and is forbidden from merging. Widening it would change the behaviour of every existing pipeline phase.

    2. A separate external scheduler / long-running worker process. Rejected: introduces a new runtime, a new credential surface and a process that must be operated. GitHub Actions already provides event triggers, cron and concurrency groups, and OpenCode already runs inside it.

    3. Keep a JSON/YAML backlog file in the repository as manager state. Rejected: it becomes a second source of truth that drifts from GitHub and invites write conflicts from concurrent agents. A pinned issue is atomic, auditable, human-editable and already covered by the label state machine.

    4. A GitHub Project as the authoritative dashboard. Rejected for now: the repository has no Project configuration and no token with project-write scope, so automated field management cannot work without a new secret. Labels are already an adequate state store; the Project stays a manual view.

    5. Manager merges nothing (recommended, not chosen). Recorded above with its costs and the fallback path.

    Consequences¶

    Positive

    • The project has an owner for sequencing, dependency order and stalled work.
    • "Next value" becomes a decision with a documented reason rather than an accident of who filed an issue.
    • Completion is evidence-based, not self-reported.
    • Autonomy, risk, budget and emergency stop become explicit, inspectable and reversible configuration instead of emergent behaviour.
    • The manager is inert until explicitly enabled, so adopting it is reversible.

    Negative / accepted

    • More moving parts, and a larger guardrail surface to review.
    • A second merge path (see above).
    • Proactive issue creation can still generate noise; bounded by the per-cycle cap and the "never create work to look busy" rule, and both are enforced by prompt contract and tests rather than by code.
    • The manager is a reasoning model and can be wrong about state. Mitigated by requiring evidence, and by status:blocked being an acceptable outcome.

    Revisit Triggers¶

    • Any observed ungated merge, or a merge attempted with --admin.
    • Branch protection refusing a legitimate manager merge, which would mean the same-identity problem needs a distinct GitHub App identity.
    • The per-cycle issue cap being hit routinely, which would mean the budget is mis-tuned rather than the manager being over-eager.
    • Drift between the manager's merge gates and the pipeline's auto-merge gates.
    • A request to make the Project authoritative, which would require adding a project-write credential.
