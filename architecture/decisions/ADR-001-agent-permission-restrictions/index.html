    ADR-001: Agent Permission Restrictions¶

    Status¶

    Accepted

    Context¶

    Baseline code review (issue #2) found two security findings in the OpenCode agent configuration: - C1: qa-engineer has unrestricted bash: allow — the most dangerous permission, inconsistent with all other agents. - C2: backend-implementer and frontend-implementer have NO permission: block at all — the two write-capable agents are least constrained.

    This violates the least-privilege principle and the repository's security rules (AGENTS.md: "Never give database write access to unknown/untrusted clients", "Household isolation is mandatory").

    Reference: Brainstorming report BR-001, GitHub Issue #5.

    Decision¶

    Apply restrictive, consistent permission blocks to all three agents following the established orchestrator/code-reviewer/security-reviewer pattern (map form with allowlist + "*": deny fallback).

    qa-engineer¶

    • edit: deny, write: deny
    • read: allow, glob: allow, grep: allow, list: allow
    • bash: { "mvn *": allow, "npm *": allow, "*": deny }
    • Explicit denies: webfetch, websearch, task, skill, external_directory

    backend-implementer¶

    • read: allow, glob: allow, grep: allow, list: allow
    • edit/write: { "src/**": allow, "pom.xml": allow, ".opencode/**": deny, "docs/architecture/security.md": deny, "*": deny }
    • bash: { "mvn *": allow, "*": deny }
    • Explicit denies: webfetch, websearch, task, skill, external_directory

    frontend-implementer¶

    • read: allow, glob: allow, grep: allow, list: allow
    • edit/write: { "frontend/**": allow, ".opencode/**": deny, "docs/architecture/security.md": deny, "*": deny }
    • bash: { "npm *": allow, "npx *": allow, "*": deny }
    • Explicit denies: webfetch, websearch, task, skill, external_directory

    Alternatives Considered¶

    1. Broad permissive (edit: allow, write: allow) — rejected: violates least privilege, inconsistent, security risk.
    2. Narrow path scoping (src/main/java/** only) — rejected: too restrictive, breaks legitimate work (resources, test fixtures).
    3. File-type patterns (**/*.java) — rejected: misses non-standard extensions; directory patterns more maintainable.
    4. Test-only bash for QA (mvn test*) — rejected: too restrictive; QA needs clean, dependency:tree, etc.
    5. Omitting explicit tool denies — rejected: implicit deny per schema, but explicit is clearer for audit.

    Consequences¶

    Positive: - All agents now follow consistent least-privilege pattern - C1 and C2 findings resolved - Defense-in-depth via sensitive path denies (.opencode/**, docs/architecture/security.md) - Explicit audit trail for all tools

    Negative: - More verbose permission blocks - Sensitive path deny list requires maintenance - Edge-case file paths (Docker, scripts) may need future allowlist extensions

    Addendum (2026-09-22, GitHub-native operation)¶

    To let agents operate inside GitHub Actions runners (the GitHub-native workflow), the bash allowlists were extended with git/gh commands:

    • backend-implementer / frontend-implementer: added "git *": allow and "gh *": allow (needed to commit, branch, push, open/update PRs). Existing edit/write path scoping and sensitive-path denies are unchanged.
    • qa-engineer: added "git *": allow and "gh *": allow (diff/evidence reporting). QA remains edit: deny — it never modifies production files.
    • orchestrator: edit/write narrowed to docs/** + AGENTS.md (reports, decisions); bash allows git * and gh * for state reconstruction and recovery reporting; task: allow (delegation) retained; websearch/ webfetch set to ask.

    This is a controlled broadening for GitHub-native execution. It does not relax the human gate: write-capable implementer access in CI additionally requires the trusted-actor rule (repository variable OC_TRUSTED_ACTORS) and per-workflow job permissions; QA and reviewers remain non-writers. The original restriction was relaxed explicitly so the change is auditable rather than silent.

    Revisit Triggers¶

    • If backend-implementer legitimately needs to edit files outside src/** and pom.xml (e.g., Docker, CI scripts)
    • If QA needs non-Maven/npm commands (docker, psql for test DB)
    • If new tools are added to the permission schema that these agents might need
    • If the agent roster changes significantly (new agents added)
